# GDI display contracts

Screen DCs use the same virtual pixel dimensions as USER32, DXGI and the active display catalogue. Retained desktop DC handles rebind after mode changes. Shrinking and expanding copies overlapping pixels, initializes new pixels to opaque black and emits a correctly sized browser frame. GetClipBox intersects the selected clip region with the current surface; resizing preserves the original selected region for later expansion. The GDI allocation budget reserves room for every catalogue desktop mode.

GetDeviceCaps uses Windows SDK indices. Window and compatible memory DCs report the display driver's capabilities; a selected bitmap controls its own dimensions and format rather than the driver's HORZRES. HORZRES, VERTRES, DESKTOPHORZRES, DESKTOPVERTRES and VREFRESH follow the active mode. CPU GDI backing pixels are 32-bit RGBA with 24 significant RGB bits, one plane and no palette. They remain RGBA8 when the separate D3D mode uses RGB565. Logical DPI is 96; physical millimetres are nominal values derived from that density and do not inspect the host monitor.

Capability flags cover implemented one-pixel solid lines, alternate-fill polygons/ellipses, rectangular and bounded complex clipping, BitBlt and StretchBlt. CreateDIBitmap and the uncompressed GetDIBits/SetDIBits paths work. RC_DI_BITMAP stays unadvertised while compressed DIB formats and full conformance remain unfinished. SetDIBitsToDevice, StretchDIBits, winding fill, full text-capability conformance, color management, mapping transforms and printer devices remain unfinished. Their capability flags stay unadvertised. Unsupported capability indices return zero, and invalid or released DCs fail.

The authored MIT [native screen fixture](../tests/fixtures/gdi-screen/README.md) queries actual SDK constants and paints/reads all four screen corners using the same native DC across 1024×768, 800×600, 640×480 and restoration. `npm run test:gdi-screen` independently checks every displayed pixel, frame dimensions and native exit status. The [report](../evidence/gdi-screen-browser-results.json) records the executable hash, compiled x86 block count, browser compilation time and per-mode observations. This proves these covered contracts; arbitrary Windows applications and DLLs remain an active goal.

GetDIBits uses the SDK's HDC/HBITMAP argument order. Metadata queries fill the native header and return success; transfers use the requested DIB width, signed height, DWORD stride and bottom scan offset. Get/SetDIBits cover 1/4/8/16/24/32-bit BI_RGB and 16/32-bit BI_BITFIELDS input, core/info/V4/V5 headers, RGB triples/quads, WORD logical-palette indices, partial row transfers and deterministic unused bytes on readback. RGB565 input converts to opaque CPU RGB; output bitfields describe the modeled RGB555/RGB888 layout. Indexed readback returns Windows' default RGB tables or the selected logical palette. A bounded color cache avoids repeating palette searches for frequent colors. The stock 20-color palette can be selected and queried; SelectPalette returns the previous handle, and custom palettes retain normal object lifetime rules.

The public **Load gdi-dib** example runs the same authored native executable with its MIT license, source archive and reproducible build.

The authored MIT [bitmap-transfer GUI fixture](../tests/fixtures/gdi-dib/README.md) uploads its unchanged native EXE, checks all six pixel depths through SDK calls, and paints a scaled bitmap. F6 uses a partial top-down upload to reverse two rows. `npm run test:gdi-dib` independently verifies every displayed pixel before and after that update and checks native exit status. The [report](../evidence/gdi-dib-browser-results.json) records its executable hash and browser-local x86-to-Wasm compilation time. These checks do not prove arbitrary software or complete GDI compatibility.

Implementation contracts were cross-checked against the Microsoft [GetDIBits](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-getdibits) and [SetDIBits](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-setdibits) interfaces and Wine's [native bitmap tests](https://github.com/wine-mirror/wine/blob/master/dlls/gdi32/tests/bitmap.c), especially partial top-down scanline placement and default indexed color tables. No Wine source or third-party executable is included in this fixture.

CreateDIBSection allocates private committed read/write guest storage for 1/4/8/16/24/32-bit BI_RGB and 16/32-bit BI_BITFIELDS. Native checked stores invalidate only affected scanlines. GDI reads decode those rows; drawing commits bounded changes to packed/BGR storage at the API boundary. Untouched pixel reserved bits, neighboring packed indices and padding survive. GetObject returns PE32 BITMAP/DIBSECTION descriptors with the real pointer. Get/SetDIBColorTable retain indexed storage, and CreateCompatibleBitmap inherits a selected DIB's format. Selected and saved DCs retain storage; DeleteObject detaches write observers and releases the mapping. Nonzero file-mapping section handles fail explicitly until that storage model is supported.

The public **Load gdi-section** example includes an authored MIT native EXE and producer DLL, source archive and deterministic build. F6 cycles direct DLL writes, GDI painting, imported CRT clearing and restoration. Native pointer-byte assertions and independent Chromium pixel scans verify all five stages (`npm run test:gdi-section`); the [report](../evidence/gdi-section-browser-results.json) records both hashes, native DLL history and browser compilation time. This extends common GUI bitmap behavior without establishing full Wine compatibility.

LoadImageA/W use the six SDK arguments and return six-argument stdcall responses when delegating icons/cursors. Bitmap loading covers named/integer resources and BMP files on the guest volume, honoring pixel offsets, full metadata/pixel bounds, independent requested dimensions and normal versus LR_CREATEDIBSECTION storage. Shared sections retain source depths, masks and scan order; unchanged-format copies preserve packed indices, padding and unused BGRA bytes. Omitted indexed table entries retain the common DIB decoder's black defaults. LR_LOADTRANSPARENT changes the first physical pixel's declared palette index to COLOR_WINDOW (or COLOR_3DFACE with LR_LOADMAP3DCOLORS); 3D mapping covers declared gray entries only. BMP/source snapshots stay unchanged, and pixels survive resource-module unload. LR_SHARED does not cache bitmaps, matching Wine's bitmap path.

The authored MIT public **Load load-images** [native fixture](../tests/fixtures/load-images/README.md) validates resources and files, native DIB pointers, module unload, sizes, color flags and typed resources. F6 edits file-loaded bitmap storage; Chromium independently scans three images before/after/restoration (`npm run test:load-images`). Its [report](../evidence/load-images-browser-results.json) records native inputs and browser compilation metrics. Sizing currently uses nearest-neighbor sampling; HALFTONE filtering, compressed/embedded-image BMPs, OEM bitmaps and sized/file icons/cursors remain unfinished. Contracts were cross-checked against the Microsoft [LoadImage interface](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-loadimagew), the MinGW SDK declaration and Wine's [image loader](https://github.com/wine-mirror/wine/blob/master/dlls/user32/cursoricon.c). No Wine source is included in this fixture.

This fixture now uses native Wine SearchPathA/W results to load real BMP and resource DLL inputs, including after changing into an authored temporary directory. The NT bridge accepts directory FILE_TRAVERSE handles and empty-directory disposition; deletion waits for the final shared handle and rejects nonempty directories, root deletion, conflicting shares and new opens/children of pending directories. The host SearchPath fallback uses the six SDK argument positions, required output sizes, real file-part pointers, extension rules, explicit lists, application/current/system/PATH order and SetSearchPathMode. Host A/W environment setters update both views. Searches stay within the existing guest-volume resolver; other drives, UNC, activation-context redirection and broader loader semantics remain separate compatibility work. The contracts were checked against Microsoft's [SearchPath](https://learn.microsoft.com/en-us/windows/win32/api/processenv/nf-processenv-searchpathw) and [SetSearchPathMode](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setsearchpathmode) declarations and Wine's [file search](https://github.com/wine-mirror/wine/blob/master/dlls/kernelbase/file.c), [path](https://github.com/wine-mirror/wine/blob/master/dlls/ntdll/path.c) and [loader](https://github.com/wine-mirror/wine/blob/master/dlls/ntdll/loader.c) implementations.

Host GUI/file/CRT path consumers now share native Wine's live normalized ProcessParameters.CurrentDirectory. A published native CURDIR handle identifies the actual opened directory; the counted UTF-16 descriptor supplies the initial directory before a handle exists. Using the published handle avoids observing the intermediate DOS-text copy during a native change and avoids decoding that text for every host path query. Host SetCurrentDirectory, CRT chdir and standard file-picker changes invoke the actual guest RtlSetCurrentDirectory_U, preserving native directory handles, locking and NT error conversion. The native current-directory buffer capacity is checked before calling that body. Host-only processes update their own normalized bootstrap directory descriptor as well. This synchronizes directory state across the supported host and native interfaces; native/host environment ownership, other volumes and broader filesystem conformance remain separate work.

The image demo's **Open bitmap…** button/F7 picker validates this direction of synchronization: the native client checks its current directory after selection, then loads a relative filename into the third panel. All supported uncompressed bitmap formats use their actual dimensions for preview. F6 edits/restores a physical RGB24 pixel; other depths remain previewable. Acceptance cancels once, then imports a visibly different authored BMP and scans its pixels across three pointer-edit stages. A separate native startup check verifies the opposite direction: a native directory change followed by relative host USER32 bitmap loading.

The host GetFullPathName A/W fallback now uses capacity argument 1, output argument 2 and four-argument stdcall cleanup. It returns required sizes and actual file-part pointers, validates output regions before writing, and supports in-place expansion. Path expansion is lexical: absent files and other-drive/UNC names can be named even when those volumes cannot be opened by the file bridge. Host expansion covers common DOS relative, rooted, drive-relative/absolute, UNC and device names, preserving the existing ANSI MAX_PATH and UTF-16 length distinction. Native Wine retains its own implementation. The authored SDK startup checks and focused fallback tests cover these contracts; extended namespaces, per-drive environment synchronization and complete Windows path conformance remain unfinished. References: Microsoft [GetFullPathName](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfullpathnamew), MinGW fileapi.h and Wine kernelbase/ntdll path implementations linked above.

File-picker sessions also retain a terminal closed state. Import callbacks queued for a dismissed picker cannot begin reading the next picker's input or replace its folders/files; callbacks finishing an asynchronous read cannot modify the reopened dialog or its submit button. Closed submit handlers do nothing. Browser acceptance retains and invokes old callbacks after cancellation and requires the new dialog and import list to remain intact. Acceptance also waits for a new visible picker request before uploading: identical titles can match the closed dialog while the next native request is still opening. This test race caused the imported-folder state mismatch observed during Chromium CI.
